# Sonoff MINI R3 factory-OTA tooling

Tools used to package and deliver a replacement BL602 firmware image through
the factory eWeLink OTA path on a Sonoff MINI R3.

This repository is specific to the BL602 Sonoff MINI R3 layout that reports
model `BL1-S04-01`. Do not use these packages for another board or for a
generic BL602 layout.

## How it works

The device remains online and downloads the package through the stock eWeLink
update path. This workflow does not use UART, does not require a flash dump,
and does not require a separately downloaded bootloader image.

The known MINI R3 factory layout has its inactive OTA slot at `0x13C000`
with capacity `0xB4000` bytes. The builder reserves the same 32-byte margin
used by the stock updater and refuses a staged capsule that cannot fit.

## Where `image_firmware_staged.bin` comes from

`image_firmware_staged.bin` is generated by the BL602 LibreTiny build step. It
contains the small in-slot OTA helper, its `LT602STG` manifest, and the
compressed application image. It is a local build artifact, not a file fetched
from the device over UART or downloaded from eWeLink.

Compile an ESPHome configuration built for the MINIR3 with the BL602 LibreTiny
backend:

```yaml
bl60x:
  board: sonoff-minir3
  framework:
    version: "1.14.0"
    source: https://github.com/Xmister/libretuya.git#bl602-integration
```

Then run a normal ESPHome compile in an environment that has the BL602
toolchain installed:

```sh
esphome compile your-device.yaml
```

The successful build log includes a line like:

```text
build_staged_image([".pio/build/<environment>/image_firmware_staged.bin"], ...)
BL602 staged OTA: updater=... compressed=... firmware=... capsule=.../737280 bytes
```

Locate the artifact in the ESPHome build tree:

```sh
find .esphome/build \
  -path '*/.pio/build/*/image_firmware_staged.bin' \
  -print
```

The usual path is:

```text
<esphome-config>/.esphome/build/<device>/.pio/build/<environment>/image_firmware_staged.bin
```

If the file is absent, the build did not reach LibreTiny's staged-image
packaging phase. Inspect the compile output for the `build_staged_image` and
`BL602 staged OTA` messages before continuing.

## Prerequisites

- Python 3.11 or newer
- `pip install -r requirements.txt`
- The `image_firmware_staged.bin` generated by the BL602 LibreTiny build
- Home Assistant with the Sonoff/eWeLink integration for the cloud trigger
- An HTTP endpoint reachable by the device

Do not commit firmware bundles, Home Assistant storage, API keys, or eWeLink
credentials.

## 1. Build the BL602 OTA package

For the current staged LibreTiny image:

```sh
python3 scripts/build_minir3_staged_ota.py \
  --staged-image /path/to/image_firmware_staged.bin \
  --hardware-version MINIR3 \
  --software-version 2026.11.6.3 \
  --output minir3.ota
```

This validates the staged-image manifest, CRCs, compressed payload hash, and
inactive-slot capacity before wrapping the image in the `BL60X_OTA_Ver1.0` XZ
package.

## 2. Wrap it for eWeLink

```sh
python3 scripts/build_ewelink_bl602_bundle.py \
  --payload minir3.ota \
  --output firmware.bundle

sha256sum firmware.bundle
```

## 3. Serve the bundle

Run the included range server on a host connected to the same LAN as the MINI
R3:

```sh
python3 scripts/serve_range.py \
  --file firmware.bundle \
  --bind 0.0.0.0 \
  --port 18767 \
  --range-status 206
```

Find the LAN address of that host:

```sh
ip -4 route get 1.1.1.1 | awk '{print $7; exit}'
```

If the command prints `192.168.4.10`, the device URL is:

```text
http://192.168.4.10:18767/firmware.bin
```

Allow inbound TCP port `18767` in the host firewall. The MINI R3 and this host
must be on reachable LAN/VLANs. From another computer on the same network,
verify both the full response and byte ranges:

```sh
curl -fI http://192.168.4.10:18767/firmware.bin

curl -f \
  -H 'Range: bytes=0-31' \
  -o /tmp/firmware-range.bin \
  http://192.168.4.10:18767/firmware.bin

test "$(wc -c </tmp/firmware-range.bin)" -eq 32
```

Use the same LAN address as `--url` when triggering the update.

## 4. Trigger the cloud upgrade

Run the trigger in the Home Assistant environment that already has an
authenticated Sonoff integration:

```sh
python3 scripts/ewelink_upgrade.py \
  --ha-config /config \
  --device-id <eweLink-device-id> \
  --model BL1-S04-01 \
  --version 2026.11.6.3 \
  --url http://192.168.4.10:18767/firmware.bin \
  --sha256 <bundle-sha256>
```

The script refuses a different model, reads the existing integration
credentials rather than storing them, sends one targeted upgrade command, and
prints the matching cloud response.

## Files

| File | Purpose |
| --- | --- |
| `scripts/package_ota.py` | Build the low-level `BL60X_OTA_Ver1.0` container |
| `scripts/build_minir3_staged_ota.py` | Wrap a LibreTiny staged image for factory OTA |
| `scripts/build_ewelink_bl602_bundle.py` | Build the multi-component eWeLink wrapper |
| `scripts/serve_range.py` | Serve one bundle over HTTP with byte ranges |
| `scripts/ewelink_upgrade.py` | Send the targeted eWeLink cloud upgrade command |

Run the local checks with:

```sh
python3 -m unittest discover -s tests -p 'test_*.py' -v
```
